Принято, переходим сразу к технической сути. Главный абсурд Ollama по умолчанию — это жесткое ограничение контекста, из-за которого ПО ломается именно при переносе на «чистый» сервер.
Когда вы запускаете Qwen в LM Studio, программа автоматически считывает максимальный контекст из файла модели (например, 32k токенов для Qwen 2.5) и динамически выделяет под него видеопамять (VRAM).
Ollama работает иначе. У неё вшит жесткий лимит, который ломает запросы «молча» или вызывает падение API.
------------------------------
## Механика проблемы num_ctx в Ollama

   1. Лимит «из коробки» равен 2048 токенам. Если вы скачали любую модель Qwen через ollama run qwen2.5, её базовый контекст составит всего 2048 токенов (около 1.5 страниц текста вместе с системным промтом и вашим кодом).
   2. Как реагирует Ollama на превышение:
   * При запросе через API /api/generate или /api/chat: Ollama не выдаст ошибку «Контекст переполнен». Она просто начнет «выталкивать» (забывать) первые токены. Ваше ПО отправляет огромный юридический документ, а модель «видит» только его финал. В итоге Qwen выдает галлюцинации или ломает структуру JSON/ответа, из-за чего парсер в вашем коде падает с ошибкой.
      * При жестком OOM (Out of Memory): Если контекст переполняется, а сервер пытается его удержать на слабой VRAM, процесс ollama runner аварийно завершается. Ваше ПО получает ошибку 500 Internal Server Error или Connection dropped.
   
------------------------------
## Два способа исправить лимит контекста
Вам нужно принудительно заставить Ollama на сервере выделить память под большой контекст.
## Способ 1. Передача параметра динамически через API (Рекомендуемый)
Вам не нужно ничего перенастраивать на сервере компании, если ваше ПО умеет отправлять параметры конфигурации в каждом POST-запросе. Добавьте объект options с ключом num_ctx:
Пример JSON-тела запроса к серверу Ollama:

{
  "model": "qwen2.5:14b",
  "messages": [
    {
      "role": "user",
      "content": "Вот текст договора на 20 страниц... [Очень длинный текст]"
    }
  ],
  "options": {
    "num_ctx": 32768
  }
}

Убедитесь, что библиотека, которую вы используете в коде (например, официальный SDK Ollama или LangChain), явно пробрасывает этот параметр в итоговый HTTP-запрос.
## Способ 2. Создание кастомной модели на сервере через Modelfile
Если вы хотите, чтобы сервер компании по умолчанию обрабатывал большие документы без изменений в коде ПО, нужно пересобрать модель внутри Ollama с нужным параметром.

   1. Создайте на сервере текстовый файл с именем Modelfile.
   2. Запишите в него следующие строки (на примере Qwen 2.5):
   
   FROM qwen2.5:14b# Устанавливаем лимит контекста в 32k токенов (32768)
   PARAMETER num_ctx 32768
   
   3. Соберите новую модель в терминале сервера:
   
   ollama create qwen2.5-legal -f ./Modelfile
   
   4. В коде вашего ПО замените имя модели с qwen2.5:14b на qwen2.5-legal.

------------------------------
## Важный нюанс с видеопамятью (VRAM)
При увеличении num_ctx кратно растет потребление VRAM (памяти видеокарты) под так называемый KV-кэш.

* Модель Qwen 2.5 14B на контексте 2k занимает около 9-10 ГБ VRAM.
* Эта же модель на контексте 32k потребует уже около 15-16 ГБ VRAM.

Если на сервере фирмы установлена карта с 12-16 ГБ VRAM, то принудительное выставление num_ctx: 32768 через API вызовет ошибку OOM (Out of Memory), и Ollama сбросит контекст в системную оперативную память (RAM), из-за чего скорость генерации упадет до 1-2 токенов в секунду, вызывая тайм-аут в вашем коде.
